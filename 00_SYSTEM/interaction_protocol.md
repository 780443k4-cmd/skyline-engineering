# Протокол взаимодействия с владельцем (Denis)

Статус: ДЕЙСТВУЕТ. Установлено 2026-08-25 прямым указанием владельца.

## Правило "сначала обсудить, потом редактировать"

Когда ответ ассистента содержит несколько (3-5) открытых вопросов владельцу, и владелец
отвечает на них по очереди — редактирование файлов НЕ начинается сразу после каждого
ответа. Порядок обязателен:

1. **Обсуждение** — владелец отвечает на вопрос(ы), ассистент проговаривает, как он понял
   ответ (своими словами, без правки файлов).
2. **План** — ассистент письменно формулирует, что именно будет сделано (какие файлы,
   какие правки) — всё ещё без правки файлов.
3. **Подтверждение** — только после явного "да"/подтверждения от владельца по всему
   плану — ассистент выполняет правки файлов одним проходом.

Причина (прямая цитата владельца, 2026-08-25): "иначе эти файлы по двадцать раз
редактируешь, мы на это тратим очень много времени". Цель — не более одного цикла
правки файлов на набор согласованных решений, вместо правки после каждого отдельного
ответа.

## Область действия

Это правило про темп именно МНОГОвопросных обменов (когда в одном ответе ассистента
несколько открытых вопросов). Не относится к:
- одиночным явным командам ("сделай X", "подтверди Y") — там правка сразу после
  подтверждения, как и раньше;
- срочным/блокирующим правкам, явно запрошенным отдельно.

## Дневной журнал (установлено 2026-09-02, дополняет "Индекс решений" выше)

Владелец ведёт `08_AUDIT/daily_log/daily_log.xlsx` — простой журнал по дням: дата +
3-7 строк "чем занимались" простым языком, без кодов. Это ПЕРВОЕ, что нужно проверить
на вопрос "что мы делали такого-то числа" или "почему ты это не помнишь" — открыть файл,
найти дату, посмотреть темы. Только если нужны детали конкретной темы — идти дальше в
`08_AUDIT/decisions/` (если тема там есть, у неё будет код DEC-NNN, указанный в строке
журнала) или в саму `01_KNOWLEDGE/`.

Правило: в конце дня, когда сессия завершает содержательную работу — добавить в
`daily_log.xlsx` строку(и) на сегодняшнюю дату (5-7 строк максимум, простым языком, без
пересказа технических деталей — детали живут в файлах, тут только "что делали"). Не
делать это после каждого мелкого действия — только один раз, когда набралось что
записать за день.

## Индекс решений (установлено 2026-09-02)

Причина: в длинной сессии старые детали диалога могут выпасть при сжатии истории — это
не сбой памяти/скиллов, а обычное свойство работы с длинным чатом. Чтобы не зависеть от
памяти диалога и не перечитывать всю базу знаний ради одного факта, каждое решение
проектного масштаба фиксируется коротким кодом в `08_AUDIT/decisions/INDEX.md`
(формат `DEC-NNN`), со ссылкой на подробный файл в `08_AUDIT/decisions/`.

Правила:
1. Решение проектного масштаба (новая стратегия, новая роль, изменение бренда/процесса,
   отклонённый/принятый инструмент и т.п.) — запись в `INDEX.md` СРАЗУ, в момент решения,
   не откладывать на потом.
2. Рутинная правка одного факта, публикация поста по уже утверждённому плану — не
   решение в этом смысле, запись не нужна (иначе индекс раздуется и потеряет смысл).
3. При любом вопросе владельца "что решили", "почему у нас так", "мы это обсуждали?" —
   сначала читать `08_AUDIT/decisions/INDEX.md` (он маленький), потом, если нужно,
   конкретный файл решения. Не полагаться на память диалога и не перечитывать всю
   `01_KNOWLEDGE/` без необходимости.
4. Владелец может сослаться на код (`DEC-004`) или на дату вместо пересказа контекста.

## Правило "проверка инструментов при старте сессии"

Установлено 2026-08-25 прямым указанием владельца: "когда комп запускается, когда
входишь в систему, сразу проверяй все инструменты, которые у тебя подключены".

Причина: нет фоновой автономной системы (см. `architecture.md`, раздел "IMPORTANT
ARCHITECTURE TRUTH") — всё происходит только в рамках диалога. При цели 2-4
поста/Reels в день нельзя терять время сессии на то, чтобы по ходу работы
обнаруживать, что нужный коннектор отвалился или не авторизован.

**Первое действие в начале КАЖДОЙ новой рабочей сессии** (до начала генерации
контента) — короткая проверка состояния:

1. Canva (`mcp__Canva__*`) — доступен ли вызов инструментов.
2. Zapier-коннекторы, от которых зависит публикация и генерация: Instagram
   (`InstagramBusinessCLIAPI`), Facebook (`FacebookV2CLIAPI`), TikTok/Buffer
   (`BufferCLIAPI`), Google Drive (`GoogleDriveCLIAPI`) — через
   `list_zapier_connections` по каждому `selected_api`.
3. Video-production коннекторы по мере подключения (Runway `App227006CLIAPI`,
   HeyGen `HeyGenCLIAPI`, ElevenLabs `App226160CLIAPI` если/когда подключены) —
   отдельно отмечать `needs_auth`/отсутствие подключённого аккаунта, не
   предполагать, что раз действие включено — значит и авторизовано.
4. Device bridge (`mcp__remote-devices__*`) — доступен ли `C:\SKYLINE_LOCAL`.

Результат проверки — коротко, одним блоком в начале ответа, только статусы
(OK / не авторизован / недоступен), без пересказа истории. Если что-то отвалилось —
сказать сразу, не дожидаясь, пока это вскроется на середине генерации контента.

## Правило "расшифровка искажений голосового ввода" (установлено 2026-08-25)

Владелец надиктовывает сообщения (печатать руками для объёма информации, которым мы
обмениваемся, физически не вариант), встроенное распознавание голоса в десктопном
приложении Claude регулярно даёт искажения — особенно на англоязычных
собственных именах внутри русской речи (пример: "SKYLINE_LOCAL" распознаётся
как "Цестка и Локал", "С с k и local one" и подобная бессмыслица). Причина
технической проблемы — на стороне приложения, не будет починена быстро (см.
переписку с саппортом Anthropic, отправлено 2026-08-25). Владелец прямо
попросил: "тебе придётся адаптироваться... чтобы ты эти крокозябры понимал,
они тратят кучу времени каждый раз на их расшифровку".

**Правило**: при получении надиктованного сообщения с фонетически похожими на
бессмыслицу фрагментами — НЕ переспрашивать сразу. Сначала попытаться
восстановить смысл по контексту и по словарю известных терминов проекта ниже
(фонетическое сходство при русском произношении английских имён — расшифровывать
эти термины, даже если написание сильно исказилось). Ответ строить так, чтобы
восстановленный термин был виден в самом ответе естественным образом (не
формулировать это как отдельный уточняющий вопрос) — так владелец видит, что
понято верно, без лишнего цикла переспроса. Переспрашивать — только если после
попытки расшифровки остаётся реальная развилка с разными последствиями
(например, неясно, какая именно из двух похожих площадок/файлов имеется в
виду), а не просто ради перестраховки.

**Словарь известных искажений** (пополнять по мере появления новых примеров):

| Как часто искажается (примеры) | Что реально имеется в виду |
|---|---|
| "Цестка и Локал", "С к Локал уан", "Skyline Local" по частям, любой набор слогов, фонетически похожий на "скайлайн ло(у)кал" | `SKYLINE_LOCAL` — корневая папка проекта |
| Любое явно нерусское/несвязное слово рядом с обсуждением площадок публикации | Instagram / Facebook / TikTok (смотреть по контексту, что обсуждается) |
| Обрывки при упоминании ролей системы | CONTENT_ARCHITECT / CONTENT_WRITER / SOCIAL_CONTENT / CREATIVE_DIRECTOR / QUALITY_CONTROLLER / FINAL_GATEKEEPER — сверять по ближайшему обсуждаемому этапу пайплайна |
| Обрывки при упоминании города/региона | Benidorm / Costa Blanca — see `hashtag_system.md` |

Общий принцип на случай термина, которого ещё нет в таблице: собственные имена
и технические термины проекта в надиктованном тексте почти всегда на английском
или являются названием файла/папки/платформы/роли — при распознавании
бессмыслицы в первую очередь проверять, не является ли это исковерканной
английской технической единицей из словаря проекта, и только потом — реальной
опечаткой смысла.

## Правило "исходники для генерации — локальная папка" (установлено 2026-08-25)

Владелец: все референс-изображения, которые он передаёт для генерации видео/
контента, физически лежат на его компьютере в `C:\SKYLINE_LOCAL\генерация
видео\`. Правило: если владелец ссылается на фото для генерации, но не
прикрепляет его в чат — сначала проверить эту папку (`device_list_dir` /
`device_stage_files`), не просить прислать повторно.

**Технический нюанс, разобранный на практике 2026-08-25 (важно не наступать
повторно)**: стейджинг файла с компьютера владельца в облачную песочницу
(`device_stage_files`) работает надёжно — это безопасный перенос байт файла.
Но чтобы такое изображение попало в Runway (`convert_image_to_video` через
Zapier), полю `promptImage` нужен либо публичный URL, либо base64 — а прямая
передача base64 картинки через вызов инструмента упирается в практический
лимит на объём текста одного вызова в этом интерфейсе (проверено: файл
~65-140КБ в base64 не удаётся надёжно провести через `Read`/цитирование без
риска обрезки/порчи данных — в отличие от переноса файлов через
`device_stage_files`/`SendUserFile`, которые двигают байты напрямую, а не
через текстовый контекст). У облачной песочницы нет обычного доступа в
интернет (проверено — `curl` наружу блокируется), поэтому самостоятельно
залить файл в Google Drive в обход этого ограничения ассистент пока не может.
**Рабочий путь на сегодня**: владелец сам закидывает референс-файл в
Google Drive (папка "фото дрон" уже публична) — тогда ассистент берёт оттуда
прямую ссылку (`https://lh3.googleusercontent.com/d/{fileId}=w1600`) и
использует её. Если это станет частой операцией — стоит вернуться к вопросу
и поискать более автоматический мост (например, если у владельца есть
папка с синхронизацией Google Drive на компьютере, которую можно подключить
к сессии как ещё одну "connected folder").

## Правило "источник темы для Reel/публикации" (установлено 2026-08-25)

Владелец забраковал первый вариант плана Reels на неделю (темы, придуманные
ассистентом по названиям папок с фото, включая повтор одной и той же темы
другим ракурсом — "херня, не годится"). Правило на будущее:

1. Если владелец даёт тему для конкретной публикации явно — используется она,
   без самодеятельности.
2. Если владелец тему не даёт — тема берётся из актуального, проработанного
   контент-плана (`content_calendar.md`), а не придумывается ассистентом с
   нуля по своим догадкам о содержимом медиатеки.
3. Полноценный контент-план (30 дней, по 1 публикации на каждую соцсеть в
   день) — отдельная задача, не срочная, делается в фоне/позже, не блокирует
   текущую публикацию. См. `content_calendar.md`, раздел "Reels — источник
   темы и статус плана".

**Соглашение владельца (2026-08-25)**: чтобы не тратить время на расшифровку
искажений самого частого термина, впредь при диктовке вместо названия
"SKYLINE_LOCAL" владелец будет говорить просто **"локальная папка"** —
это всегда означает корневую папку проекта (`C:\SKYLINE_LOCAL` на компьютере
владельца / `SKYLINE_LOCAL` в рабочем окружении ассистента). Понимать это
сочетание однозначно, без уточнений.

## Правило форматов выдачи файлов (установлено 2026-09-01)

Владелец прямым указанием (2026-09-01): все файлы, которые ассистент генерирует и
выдаёт по ходу работы (стратегии, планы, брифы, отчёты, любые рабочие документы),
делаются **только в формате `.md`**. Не PDF, не DOCX, не XLSX — "нет смысла делать
текстовые документы... они нужны в первую очередь для вас (для AI), вам проще
понимать MD, это быстрее, это эффективнее".

Исключение — форматы, для которых `.md` физически не подходит по своей природе:
таблицы для прямого заполнения владельцем (напр. `.xlsx`, когда нужен цветной
чек-лист для ручного ввода ответов), готовые медиафайлы (изображения/видео),
и данные, которые по контракту площадки должны быть в другом формате (JSON для
`02_TASKS/`, `00_INDEX/` и т.п. — уже существующая практика системы). Во всех
остальных случаях — MD по умолчанию, без дополнительного согласования формата.

## Правило по каруселям — авто-слайдшоу с музыкой, а не свайп (установлено 2026-09-01)

Уточнение к `05_CONTENT/publishing_rules.md` п.11 и `05_CONTENT/creative_director_playbook.md`
п.3. Прямая формулировка владельца: карусели как формат **не отменяются** — "карусели
генерим, они работают, это нормальная тема" — но не в прежнем виде (набор из 8-10
отдельных JPG-слайдов для свайпа в ленте, где автоматически видна только первая
картинка, а остальные листаются вручную — "получается ерунда").

Новый рабочий формат: те же слайды карусели (то же содержание, та же бренд-палитра
из `01_COMPANY/brand.md`), но собранные в **видео** — картинки идут одна за другой
**автоматически** (слайд-шоу/Ken Burns), с наложенной музыкой через ffmpeg — то есть
технически это Reels/видео-carousel, а не фото-пост для свайпа. Пайплайн сборки —
тот же, что уже использовался для готовых Reels (`05_SOCIAL/Reels/Generated/`), только
источник кадров — карусельные макеты (A/B/D и новые), не отдельно снятый видеоряд.
